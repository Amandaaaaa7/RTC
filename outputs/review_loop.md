# 阶段4：对抗性评审循环 — 语音代码迁移与 Pi Zero 2W 优化

## 评审对象

阶段2推荐的 **方案 C（混合分层）**，具体实现路线为：先完成方案 A 的 MVP（解决 ALSA 冲突、接入 main.py、眼睛简单联动），再抽象为可插拔后端，最后加入简化记忆/XP 与完整眼睛状态机。

## 第1轮：技术实现风险

### 评审视角

从代码实现难度、ALSA 独占问题、线程安全、依赖兼容性等角度攻击方案。

### 评分

| 维度 | 分数（1-10）| 说明 |
|------|------------|------|
| ALSA 独占问题解决 | 7 | 复用 MicMonitor 回调可行，但回调消费者需避免阻塞 |
| 线程安全 | 6 | VoiceModule 推理线程与 MicMonitor 回调线程共享队列，需仔细设计 |
| 依赖兼容性 | 6 | pydub 依赖 ffmpeg，Pi 上可能未安装；dashscope 下载曾失败 |
| 播放接口改造 | 8 | `speaker.play_buffer` 逻辑清晰，改动面小 |
| **综合** | **6.75** | 技术实现有把握，但细节处容易埋坑 |

### 主要短板

1. **回调阻塞风险**：如果 `VoiceModule` 在回调中做耗时操作（如 VAD 计算），会拖慢 `MicMonitor`。
2. **pydub 依赖 ffmpeg**：Pi OS Lite 默认没有 ffmpeg，离线安装 whl 不够，还需复制二进制。
3. **播放与录音并发**：虽然 capture 与 playback 使用不同方向，但部分廉价 I2S 声卡驱动可能不支持全双工同时打开。
4. **API Key 泄露风险**：`voice/config.py` 中可能硬编码 Key 并被误提交。

### 最小修复动作

1. 回调中只做 `queue.put(frame)`，所有处理放到独立消费线程。
2. 用 `pydub` 时提供离线安装 ffmpeg 的说明；或优先使用 Python 标准库 `wave` 播放 WAV，MP3 解码使用 `miniaudio` / `soundfile` 等更轻量库。
3. 在 `speaker.py` 中增加 try/except 与 ALSA 设备重试；若全双工失败，考虑使用 `dmix`/`dsnoop` 插件。
4. 将 `voice/config.py` 中的 Key 读取改为环境变量优先，并在 `.gitignore` 中忽略本地配置文件。

## 第2轮：实时性 / 性能

### 评审视角

从 Pi Zero 2W 的 CPU、内存、网络延迟角度，攻击方案是否能在目标硬件上达到可接受的交互延迟。

### 评分

| 维度 | 分数（1-10）| 说明 |
|------|------------|------|
| 端到端延迟（云端） | 6 | Google ASR + DashScope LLM + 预录音频 ≈ 1.5-3s，可接受但偏慢 |
| CPU 占用 | 7 | 云端模式下 Pi 主要负责录音、播放、眼睛动画，CPU 压力不大 |
| 内存占用 | 7 | 不加载本地模型时，内存压力可控 |
| 眼睛动画帧率 | 7 | 当前 EyeDisplay 25fps，增加状态机后可能略降 |
| **综合** | **6.75** | 性能基本达标，但延迟优化空间明显 |

### 主要短板

1. **Google ASR 国内不稳定**：可能导致延迟抖动甚至失败。
2. **云端 LLM 调用是串行瓶颈**：每次对话都要等待 LLM 返回，无法并行预加载。
3. **眼睛动画与语音状态同步不够细**：仅 4 个粗粒度状态，缺少“识别中”“情绪涌现”等过渡态。
4. **没有预连接或连接池**：每次请求都新建 HTTPS 连接，增加延迟。

### 最小修复动作

1. 将默认 ASR 从 Google 改为 DashScope（国内稳定），并保留 Google 作为 fallback。
2. 在 LLM 调用前预发送一个“请只返回情绪标签”的 system prompt，控制输出长度在 5 个 token 以内。
3. 使用 `requests.Session()` 或 `httpx.Client()` 复用连接。
4. 眼睛状态机增加 `VAD_TRIGGERED`、`ASR_PENDING`、`LLM_PENDING` 等过渡态，让等待期间也有动画反馈。

## 第3轮：可维护性 / 运维

### 评审视角

从代码结构、配置管理、日志、部署、长期运行稳定性角度攻击方案。

### 评分

| 维度 | 分数（1-10）| 说明 |
|------|------------|------|
| 模块化程度 | 8 | 后端抽象层、Memory、XP、EyeState 拆分清晰 |
| 配置管理 | 5 | 当前 config.py 硬编码路径与 Key，不够灵活 |
| 日志与可观测性 | 6 | 主要依赖 print，缺少结构化日志与指标 |
| 部署脚本 | 5 | 离线依赖安装流程已写，但未自动化 |
| **综合** | **6.0** | 可维护性中等，配置与运维是明显短板 |

### 主要短板

1. **配置分散**：`voice/config.py`、`speaker.py`、`mic.py`、`eye_display.py` 都有硬编码参数。
2. **日志非结构化**：print 输出难以聚合与告警。
3. **缺少健康检查**：无法自动发现 ALSA 设备消失、内存耗尽等故障。
4. **模型/资源文件管理缺失**：本地模型下载、校验、版本管理未定义。
5. **热更新困难**：修改语音策略需重启整个 `main.py`。

### 最小修复动作

1. 引入统一的 `config.yaml` 或 `.env` 配置，各模块从中读取，避免硬编码。
2. 使用 Python `logging` 模块替换 print，按模块分级输出到文件。
3. 在 `VoiceModule` 中增加 `health()` 方法，周期检查 ALSA 设备、内存、API 可用性。
4. 增加 `scripts/download_models.sh` 与 `scripts/check_env.py` 一键准备环境。
5. 将语音策略参数（阈值、超时、情绪列表）放入配置文件，支持不重启重载。

### 评审视角

从现有代码库约束、硬件生态、第三方服务可用性、长期演进角度攻击方案。

### 评分

| 维度 | 分数（1-10）| 说明 |
|------|------------|------|
| 与现有架构兼容 | 8 | 基于 MicMonitor、EyeDisplay、speaker.py 扩展，符合 CLAUDE.md 规则 |
| 硬件生态 | 7 | I2S 麦克风/扬声器在 Pi 上成熟，但全双工需谨慎 |

| 开源替代路径 | 7 | SenseVoice + Piper 为离线路径预留 |
| **综合** | **7.0** | 生态约束总体可控，但云服务商依赖是隐患 |

### 主要短板

1. **DashScope API 绑定**：如果未来 Key 失效或额度不足，系统可能直接停摆。
2. **Edge TTS 免费性不确定**：微软可能随时限制非官方客户端。
3. **PyAlsaAudio 维护活跃度一般**：长期可能有 Python 版本兼容问题。
4. **缺少测试覆盖**：当前没有单元测试，重构时容易回归。

### 最小修复动作

1. 在 `voice/backends/` 中预留所有后端的统一接口，确保替换供应商只需改配置。
2. 默认使用预录音频库，将对云服务的调用降到最低。
3. 为 `voice/backends/base.py` 与 `voice/module.py` 编写单元测试，使用 mock 后端。
4. 在 README 中明确记录各后端的许可与潜在风险。

## 最终最小修复动作清单

进入实现阶段前必须完成：

1. **统一配置**：使用 `.env` 或 `config.yaml` 管理路径、设备、API Key、阈值；`voice/config.py` 只作为读取入口。
2. **回调隔离**：`MicMonitor` 回调只做入队，VoiceModule 使用独立线程消费。
3. **ASR 默认 DashScope**：将默认 ASR 改为 DashScope 以提升国内稳定性，Google 作为 fallback。
4. **结构化日志**：引入 `logging` 按模块输出，至少包含 `voice`、`mic`、`speaker`、`eye` 四个 logger。
5. **健康检查**：`VoiceModule` 启动前检查 ALSA 设备、API Key、音频目录；运行中周期性检查内存。
6. **眼睛状态扩展**：在 `EyeDisplay` 中增加 `VAD_TRIGGERED`、`ASR_PENDING`、`LLM_PENDING`、`SPEAKING` 等状态。
7. **去掉 pydub 强依赖**：预录音频统一转换为 WAV 或提供 ffmpeg 离线安装说明；播放优先使用 `speaker.play_buffer` + 标准库。
8. **单元测试骨架**：为 `voice/backends/base.py` 与 `voice/module.py` 提供 mock 测试。

## 结论

**继续推进方案 C，但必须先完成上述 8 项最小修复动作。**

当前方案在 Pi Zero 2W 上具备可行性，且与现有架构兼容。主要风险集中在配置管理、回调阻塞、云端服务稳定性三个方面，均可以通过工程手段缓解。没有单一风险会推翻整个方案，因此不建议回退到方案 A 或 B。

进入实现阶段后，按阶段3周计划执行，优先完成前 3 项最小修复动作（统一配置、回调隔离、ASR 默认 DashScope），再逐步扩展眼睛状态机与记忆/XP 系统。
